# Lessons

- （初期作成）ユーザー修正指示を受けたら、再発防止ルールをこのファイルへ追記する。
- フロント検証の依頼が来たら、ホスト直実行ではなく `docker compose run --rm frontend ...` で先に再現確認する。
- 事業提案/ヒアリング資料を作るときは、ユーザーの実績と信頼根拠（役職・経験）を最初に明示し、個別課題ではなく共通課題として扱う前提を文章化する。

- LPの配色変更は、情報階層（強調カード）の意図を先に確認し、視覚差分が大きい変更は段階適用する。

- レイアウト変更時はカードグリッドの総和だけでなく、次段の空き領域（孤立カード）を必ず確認し、必要なら明示的に全幅指定する。

- スマホのチャート崩れは幅だけでなく固定高さの過剰設定で起きるため、カードごとにモバイル高さを個別調整する。

- グリッドのPC用 `grid-column: span N` はSPで必ず `1 / -1` に上書きし、暗黙グリッド生成によるカード幅崩れを防ぐ。

- 本PJでは、要件変更の種類に応じてCOO/デザイナーのレビューを実装前または実装直後に必ず挟む（運用・KPIはCOO、UI/UXはデザイナー）。
- 画面ごとの方針を固定する: 検索画面(`/`)は情報密度重視の業務UI、LP(`/rowing-results`)は訴求重視。レビューと実装はこの役割分離を前提に行う。
- 年度大会データの取込依頼では、既成ファイルの転記ではなく、日本ローイング協会の年度ページを起点に公式結果を収集する工程から含める。
- データ取込スクリプトがホストの古い言語・ライブラリで動かない場合、スクリプトを互換修正せず、プロジェクトに適したコンテナ環境から実行する。

・EC2中心の構成をECS Fargateへ段階移行
デプロイ・監視・ロールバック手順を再設計し、運用負荷と障害時の復旧時間を削減。移行期間中のサービス影響を抑えながら安定運用に着地。

・CIをCircleCIからGitHub Actionsへ移行
既存ジョブを棚卸しし、並列化とキャッシュ方針を見直し。開発フローに馴染む形で標準化し、変更追従しやすいCI基盤へ改善。

・E2E/System Spec導入と品質改善サイクルの構築
重要機能を中心に回帰テストを整備し、障害の早期検知を強化。テスト資産をチーム内で継続的に拡張できる運用ルールを設計。

・生成AIを活用したソースコード添削機能を開発
要件整理から実装・評価まで担当し、学習者向けのフィードバック体験を向上。プロダクト価値に直結する機能として運用へ接続。

・生成AI 全社活用プロジェクト（PL）
生成AIの全社導入・定着をPLとして推進中。PJ計画の策定からツール選定（n8n・Dify）、検証、環境整備まで、横断的に担当。
