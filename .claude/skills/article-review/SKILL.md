# 記事の読者体験・推敲・校正レビュー

`frontend/app/articles/` 配下のメディア記事を、3段階でチェックする。

1. **読者体験(article-reader-reviewer)**: サブエージェントで、想定読者が知りたいことに届く順番か・見出しと表だけで分かるか・次に行くページへの導線があるかを見る。段落の移動や見出しの付け替え、表の列の取捨選択など、**構成の変更**がここで決まる。
2. **推敲(yomiyasu)**: メイン側で `yomiyasu` スキルを読み込み、記事の日本語を整える。
3. **校正(article-proofreader)**: サブエージェントで事実・データ整合性、日本語校正、AIっぽさ(humanizer-ja準拠)、内部リンク健全性をチェックする。

構成が動いてから文章を整え、文章が固まってから校正に入るので、順番は必ず 1 → 2 → 3。校正の後に本文を書き直したら、変えた段落だけでも 2 からやり直す。

**1 と 3 は、レビュー側の「判定」が合格になるまで「修正 → 再レビュー」を繰り返す**(品質ループ)。1回で終わらせない。

- 各段階の上限は **3 回**。3 回目でも要改善なら、残った指摘と見送る理由を書いてユーザーに判断を仰ぐ(無限に回さない)。
- 再レビューのプロンプトには、前回の報告の全文と、メイン側が「何をどう変えたか / 何を理由付きで見送ったか」を必ず付ける。レビュー側はそれを見て前回の指摘を1件ずつ判定する。
- 見送ってよいのは、記事の方針(上の「記事の方針」の3点)に反する提案と、削ると他に無い事実が消える提案だけ。好みの違いで見送らない。
- 1 の構成変更で本文が動いたら、2 は最後の 1 が合格した後に 1 回だけ回す。3 で本文を書き直したら、変えた段落だけ 2 の基準で整えてから 3 を回し直す。

## 記事の方針(書くときも、各段階のレビューでも守る)

- **筆者の視点を入れない**。記事は収録データと一次情報(JARA の要項・大会ページ)の事実だけで書く。出身校・OB視点・見どころ予想・個人的評価は書かない。
- **数字を手書きしない**。本文の数字はビルド時集計で出す。
- **団体ごとの比較は男女別にする**。優勝回数・メダル数・勢力図のランキングなど、団体同士を並べて比べる図表と文は、男子種目と女子種目を分けて集計し、別々に見せる(2026-10-22 のユーザー指示)。男子と女子は種目も勝つ団体も違い、混ぜると男子の種目数が多い団体が上に来るだけで、どちらの勢力図も読めなくなる。
  - 種目の判定は `event_name` の「男子」「女子」で始まるかで行う。混合種目があれば別枠にする。
  - 男女の図を並べるときは、棒の物差しを両方で揃える(並べた長さが同じ回数を表すように)。
  - 例外は、1つの団体の成績をまとめる場面(団体ページ、ある団体の通算)と、片方の性別のデータがほとんど無い場面。例外にしたら、男女を合わせて数えていることを本文か注記に書く。

## いつ使うか

- **記事を新規作成した後、および本文・数字を大幅に編集した後は必ず実行する**(公開前の最終チェック)。
- ユーザーが「記事を校正して」「記事をレビュー」「読者目線で見て」「文章を読みやすくして」と依頼したとき。「読者目線で」「読み手の体験」だけを頼まれたときは 1 だけを回す。

## 手順

### 0. 対象を特定する

- 直前に作成・編集した記事があればそれを対象にする(`git status` / `git diff` で変更範囲を確認)。
- 指定があればそれに従う。
- 対象は本文の `page.tsx` だけでなく、`frontend/lib/articles.ts` の `title` / `description` と、`page.tsx` 内の OG 画像の `title` / `subtitle` も含める(検索結果とSNSに出る文章なので、本文と同じ基準で整える)。

### 1. article-reader-reviewer で読者体験を見る

1. Agent ツールで `subagent_type: "article-reader-reviewer"` を起動する。プロンプトに以下を含める:
   - 対象記事のファイルパスと、`frontend/lib/articles.ts` の該当エントリ。
   - 記事の種類(大会ガイド / 年別の結果記事 / 分析 / 用語集・入門)と、分かっていれば公開のタイミング(大会前・大会直後など)。
   - ユーザーが想定読者を指定していればそれを渡す。無ければエージェント側の既定(記事の種類ごとの読者と場面)に任せる。
   - 制約の再掲: 上の「記事の方針」3点(筆者の視点を入れない、数字は手書きしない、団体ごとの比較は男女別)。
2. サブエージェントの結果はユーザーに直接表示されないため、報告内容を要約せず**そのまま**ユーザーに提示する。
3. 「高」「中」の指摘をメイン側で実装する(段落の移動・見出しの付け替え・導線の追加・表の列の削除)。「削ってよい候補」は、削る段落・表にしかない事実が無いことを確かめてから削る。他に無い事実がある場合は削らず、見送る理由として報告に書く。
4. `npx tsc --noEmit` で壊れていないことを確かめ、前回の報告と変更内容を付けて再レビューする。**判定が合格になるまで 3 → 4 を繰り返す**(上限 3 回)。
5. 合格したら、各回の判定と最終的に残った「低」の指摘を一覧にしてユーザーに見せ、2 へ進む。

### 2. yomiyasu で推敲する(メイン側で実施)

1. Skill ツールで `yomiyasu` を読み込む。ドメインは `essay`(メディア記事)、立場は原則「説明」として扱う。
2. 記事から**日本語の地の文だけ**を取り出す: リード文、見出し、段落、注記、表のキャプション、`articles.ts` の title/description。JSX の構造、`{}` 内の式、数値、固有名詞(大学名・大会名・種目名・選手名)、リンク先、`<Link>` のアンカーテキストに含まれる固有名詞は対象外。yomiyasu の「意味の保持」「情報の不増補」はそのまま適用し、数字や集計条件の説明は一字も変えない。
3. 取り出した地の文をスクラッチディレクトリにテキストで保存し、同梱スクリプトで静的検査と差分検査を回す:
   ```bash
   python3 ~/.claude/skills/yomiyasu/scripts/yomiyasu_lint.py <元の文.txt>
   python3 ~/.claude/skills/yomiyasu/scripts/yomiyasu_diff.py <元の文.txt> <書き直した文.txt> --stance=説明
   ```
   検出結果は候補として扱い、専門用語や評価を担う語は無理に言い換えない。修正は1回のみで、スクリプトを回し直す往復はしない。
4. yomiyasu の出力フォーマットのうち「変えたところ」「残したAIっぽいところ」「書き手に確かめたい点」をユーザーに提示する。「書き手に確かめたい点」がある箇所は、ユーザーの回答を待ってから本文に反映する。
5. 書き直した文を `page.tsx` / `articles.ts` に反映する。JSX の構造や式は動かさず、文字列だけを差し替える。

### 3. article-proofreader で校正する

1. Agent ツールで `subagent_type: "article-proofreader"` を起動する。プロンプトに以下を含める:
   - 対象記事のファイルパス(例: `frontend/app/articles/<slug>/page.tsx`)と、参照している lib(`articles.ts`, `results-data.ts`)。
   - 記事の狙い・データの集計条件(分かっていれば)。
   - 「実データを自分で再集計して本文の数値を検証すること」を明示的に指示する。
   - 団体を並べて比べる図表・文が男女別に集計されているかも確かめるよう指示する(「記事の方針」)。
   - yomiyasu の推敲を済ませていることと、その「変えたところ」の要点(校正側が同じ箇所を逆戻しにしないため)。
2. サブエージェントの結果はユーザーに直接表示されないため、報告内容を要約せず**そのまま**ユーザーに提示する。
3. 「要修正」に挙がった事実誤り・データ不整合・誤字はメイン側で実装する。「推奨」のうち AIっぽさ・読みやすさの指摘も記事の方針に反しない限り実装する(方針に反するものは理由を付けて見送る)。
4. 前回の報告と修正内容を付けて再校正する。**判定が合格になるまで 3 → 4 を繰り返す**(上限 3 回)。本文の段落を書き直した場合は、その段落だけ 2 の基準で整えてから再校正に出す。
5. 合格したら、各回の判定と残った「推奨」を一覧にしてユーザーに見せ、ビルド確認と本番反映まで通常フローで行う。

## 注意

- 読者体験(1)と校正(3)はレビューのみを行い、サブエージェント側ではコードを変更しない。構成の変更、推敲(2)の反映、校正結果の実装はメイン側で行う。
- 読者体験(1)と校正(3)の「構成・読みやすさ」が重なったときは、情報の順番・導線・表の取捨選択は 1、リード文の要点・見出しの論理・専門用語の補足・まとめの持ち帰りは 3 の指摘を採る。
- humanizer-ja と yomiyasu はどちらも「意味を変えない」が前提で、役割が違う。humanizer-ja は AIくさい定型表現の検出と人間らしい言い換え、yomiyasu は主述の対応・文のつながり・文末の立場・装飾記号の整理を担う。同じ箇所で言い換えの好みがぶつかったときは、記事の声として先に採用している humanizer-ja を優先する。
- SEO・拡散の観点は `marketing-review` スキル(marketer)が担当。役割が重複したら、事実正確性・日本語・読みやすさはこのスキル、検索流入・シェアは marketer に振り分ける。
